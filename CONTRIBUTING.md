# Contributing to OpenEMT

Contributions are welcome. This page is short and everything in it is load
bearing.

## Before your first merged pull request

**Sign the CLA.** Add a line to [CONTRIBUTORS.md](CONTRIBUTORS.md) in your
first pull request, as described in [CLA.md](CLA.md). This is required, and
the reason it is required is explained there: OpenEMT is dual licensed, and
that only works if the rights to the whole work are held in one place.

## The gate every change must pass

```bash
python build.py && node smoke_test.js && node api/test_api.js
```

Both test suites must be green before and after your change. `smoke_test.js`
is not a formality: it checks physics against independently derived analytical
results, and a failure usually means the answer is wrong rather than that the
test is stale.

If you change anything under `src/`, rebuild. `index.html` is generated by
`build.py` and is committed, so a change to `src/` with a stale `index.html`
is an incomplete change.

## If you are touching the solver or a block model

Read [SPEC.md](SPEC.md) first, particularly section 1 (architecture and the
critical invariants) and section 2 (the companion-model derivations).

New block models need a derivation in SPEC section 2 **before** the
implementation, and a validation check in `smoke_test.js` against something
independent: a closed-form solution, a published reference case, or a
separately solved equivalent circuit. "It looks plausible on the plot" is not
validation. Several traps in this codebase produced results that looked
entirely reasonable and were wrong; the known ones are listed in
[DECISIONS.md](DECISIONS.md) and in the repository guidance.

## Cross-checking a block against a commercial tool

**This is the most valuable contribution available to the project right now,
and it does not require writing any code.**

Every block is checked, but all the references are in-house: closed-form
phasors, a self-contained nodal helper, and structural properties. Zero blocks
have been cross-checked against a commercial or independently-developed EMT
program, because the maintainer does not have a licence for one. That gap is
the reason the README carries an AS-IS notice, and it is the last piece of
SPEC section 5 item 9.

If you have PSCAD, PSS/E, PowerFactory, EMTP-RV or similar at work or at
university, and twenty minutes:

1. Pick a block from the **High** row of the scoreboard in
   [VALIDATION.md](VALIDATION.md). Those are the ones where an external
   reference would actually tell us something new.
2. Build the equivalent case in your tool. Keep it small; one disturbance is
   plenty.
3. Open an issue with the **Block validation report** template and attach the
   waveform CSV, your parameters, and the OpenEMT case file if you built one.

It does not need to be exhaustive or polished. One trace and the parameters is
a real result.

Two things worth saying plainly. **A disagreement is more useful than an
agreement**, and it will be published either way: the purpose of that file is
to be accurate about what is known, not flattering. And **do not send anything
your licence or employer does not permit you to share** — a description of the
model and the numbers is useful on its own, and we do not want your vendor's
files.

## Record why, not just what

Significant design decisions get a dated entry in
[DECISIONS.md](DECISIONS.md) with one to three sentences of reasoning. Correct
an earlier entry by appending a new dated one, never by rewriting it. This is
the project's memory across long gaps, and it is why the codebase can explain
its own odd corners years later.

Speculative ideas go in [IDEAS.md](IDEAS.md), not into the roadmap, and not
into the code.

One rule about IDEAS.md and the SPEC roadmap that is easy to miss: keep
descriptions of unbuilt methods at concept level. Both files are published, and
a detailed derivation of something not yet built has consequences beyond the
repository.

## Accuracy language

OpenEMT is beta and its results are not certified. Please do not describe a
block as "validated" or "verified" as a yes or no. Say what it was checked
against, and how closely. [VALIDATION.md](VALIDATION.md) carries the per-block
reference class, and a change to a block's behaviour means its entry needs
rechecking. A stale accuracy claim is worse than none, because someone will
rely on it.

## Style

Match the surrounding code. The codebase has a consistent voice: terse file
headers explaining the module's contract, comments that say why rather than
what, and no framework dependencies anywhere in `src/`. The browser build is a
single self-contained file with no external requests, and that property is not
negotiable.

## Reporting a problem

A wrong number is a bug and the most valuable kind of report. Please include
the circuit JSON, the run settings, what you expected, what you got, and where
your expectation comes from. A case file plus a reference is immediately
actionable.

For security issues, see [SECURITY.md](SECURITY.md).

## Questions

Open a GitHub issue. That keeps the answer where the next person with the same
question will find it.

For commercial licensing, see [LICENSING.md](LICENSING.md). For security
issues, see [SECURITY.md](SECURITY.md), which uses GitHub's private reporting
channel rather than a public issue.
